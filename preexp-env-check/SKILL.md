# 实验前环境检查 Skill

## 这个 Skill 做什么

功耗实验启动前，代替人工远程登录服务器逐项核对环境。检查范围**严格限定为只读检查**，
通过 SSH 在服务器上执行既定命令、解析输出、与判据比对，产出一份环境检查报告，
给出"可开跑 / 不可开跑 + 原因 + 修复建议"的总体结论。

## 何时触发（slide5 第1项）

用户表达下列意图时触发：
- "我要跑功耗实验了，帮我检查一下环境"
- "实验前环境检查" / "lptest 前检查"
- "检查一下服务器环境能不能跑实验"
- "跑实验前帮我看看 pid 生效没、驱动对不对"

## 明确不负责（slide5 第2项，边界即能力边界）

本 Skill **不做**以下事情，触发到这些请求应说明边界并停止：
- ❌ 不执行实验本身（不跑 `HY_PID_run.sh`，那是跑实验不是检查）
- ❌ 不拉起 vllm 服务（`run_tp4ep_401.sh` 属于启动服务，超出检查范围）
- ❌ 不修改任何文件（不改 `HY3_0_run_pid.sh` 里的日期等配置）
- ❌ 不设置环境变量（`export ASCEND_RT_VISIBLE_DEVICES` 属于执行操作；
       本 Skill 只**读回核对**该变量是否已正确设置）
- ❌ 不分析实验后数据（那是另一套分析流程）
- ❌ 不自动修复服务器配置（发现不通过只报告，修复动作交还用户；
       唯一例外见下方"failed 17 自动重试"）

## 必需输入（slide5 第3项）

触发后先确认以下输入，缺失则向用户**澄清，不臆测**（slide7 边界：不把歧义悄悄吞掉）：

1. **SSH 连接信息**：主机、端口、用户名、密钥路径或密码
   （从环境变量 `PEEC_SSH_HOST/PORT/USER/KEY` 读取，不硬编码进脚本——安全红线）
2. **lptest 工具路径**：默认 `/data/ts-home/p00954667/tool/lptest0d0`，可由用户覆盖
3. **lpmi_tool 路径**：默认 `/data/ts-home/p00954667/tool/lpmi_tool`，用于 failed 17 重试
4. **turbocfg 参数**：默认 `17 9 50`，可由用户覆盖

> 说明：pid 数值不比对，只检查输出是否含 `p[...]i[...]d[...]` 格式（见判据）。

## 前置条件（slide5 第4项）

- 本地 Python 3 + paramiko（`pip install paramiko`）
- 服务器网络可达、用户具备 SSH 权限
- 检查命令所需权限（执行 lptest/lpmi_tool、读环境变量）

## 执行步骤

1. **确认输入**：按"必需输入"清单核对，缺失项向用户澄清后再继续。
2. **第 1 项检查：固件驱动 + pid 生效**
   - 调用 `scripts/check_firmware_pid.py`
   - 远程执行 `lptest0d0 turbocfg 17 9 50`，解析输出：
     - ✅ 通过：输出含 `p[...]i[...]d[...]` 格式 + `cmd turbocfg exec succ`
     - ❌ 失败 A：输出含 `failed 7` → 固件驱动版本不对，**停止**
     - ❌ 失败 B：输出不含 `p[...]i[...]d[...]` 格式 → pid 参数未生效，**停止**
     - ⚠️ 失败 C：输出含 `failed 17` → **自动重试一次**（见下），仍失败则**停止**
   - **failed 17 自动重试逻辑**（唯一允许的"修复尝试"，仍是检查的一部分）：
     1. 后台拉起 `lpmi_tool --device-id <npu> --query-info --power-sampling ... --try-repair > lpmi_<npu>.log 2>&1 &`
     2. 等待 5 秒
     3. 通过 SSH channel 发送 `\x03`（Ctrl+C）打断 lpmi_tool
     4. 重新执行第 1 项检查命令
     5. 仍 failed 17 → 停止并报告
3. **第 2 项检查：NPU 可见设备**
   - 调用 `scripts/check_npu_visible.py`
   - 远程读回 `ASCEND_RT_VISIBLE_DEVICES` 环境变量，核对是否为预期值
   - 预期值从环境变量 `PEEC_EXPECTED_VISIBLE` 读取，未设置时默认 `0`（单卡机器）；
     多卡服务器可 `export PEEC_EXPECTED_VISIBLE=4,5,6,7` 覆盖
   - ✅ 通过：值 == 预期值
   - ❌ 失败：值不符或未设置 → 报告"需在服务器上 export ASCEND_RT_VISIBLE_DEVICES=<预期值>"，**停止**
   - 注：本 Skill **不替用户执行 export**（越界），只读回核对并报告。
4. **汇总报告**：按 `assets/report_template.md` 格式生成检查报告，给出总体结论。

## 关键判断（slide5 第6项）

- **两项检查均为关键项**。任一不通过 → 立即停止，报告"不可开跑"。
- 本 Skill 没有非关键项告警分支（当前两项都是关键）；后续若新增非关键检查项，
  在 `references/check_items.md` 里标注分级，Agent 据此决定"告警继续"还是"停止"。

## 停止与反馈（slide5 第7项）

**触发停止的条件**：任一关键项检查返回 fail（含 failed 17 重试后仍失败）。

**停止时必须报告**（每条缺一不可，对应 slide10"从结论反查原始证据"）：
1. 哪一项检查不通过
2. 实际值（命令原始输出）vs 预期判据
3. 失败分类（failed 7 / pid 未生效 / failed 17 重试失败 / NPU 可见设备不符）
4. 建议修复动作（从 `references/check_items.md` 取对应 fix_hint）
5. 明确结论：**当前环境不可开跑，修复后请重新触发检查**

## 证据可反查（slide10 验收红线）

报告中每一项检查结论都附**原始命令输出**（stdout/stderr 原文）。
用户能从"不通过"结论点击/回溯到具体命令的完整返回，验证 Agent 没有误判。

## 安全红线（slide9）

- SSH 密钥/密码**绝不硬编码**进脚本或写进 skill 仓库，一律从本地环境变量读取。
- 全部检查命令为**只读**（除 failed 17 的 lpmi_tool try-repair，那是既定修复尝试且在检查范畴内）。
- 不修改服务器配置文件、不删除任何文件。
- 报告中的原始输出如含敏感信息（IP/路径/账号），由用户自行决定是否随报告外发。

## 与 Agent 的分工（答辩追问准备）

- **脚本负责确定性判断**：跑命令、解析输出、比对判据、返回结构化 pass/fail。
  可测、可复现，不依赖大模型臆断。
- **Agent 负责调度与交互**：确认输入、按序调用脚本、把结构化结果组织成自然语言报告、
  在不通过时给出修复建议。这是 Agent + Skill 的正确分工。
